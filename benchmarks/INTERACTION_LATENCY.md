# Interaction latency diagnostic

> Historical evidence: results and “current source” below refer to the dated
> experiment, not a new validation of this checkout. Only the
> [selected evidence](README.md) is included; entries marked “private archive”
> are unavailable in this repository. Original SHA values and recorded commands
> describe the original run and may require private revisions or inputs. See
> [provenance and replay limits](../docs/development/PUBLICATION.md).

This benchmark drives the production `FractalView` scroll, pinch, trackpad and
mouse-drag handlers in a visible JavaFX window. It separates transformed-image
preview, preparation of the requested frame, callback delivery, exact target
base pixels (including cache reuse), first AA tile and completed rendering.
The normal application leaves recording disabled.

## Measurement boundaries

- `input_*`: entry into the JavaFX event handler. Events are generated by the
  benchmark, so mouse/trackpad hardware and OS input-delivery latency are excluded.
- `preview_publish`: the existing image's transform has been changed. This is
  immediate visual feedback, not new fractal samples.
- `render_start`: entry into the controller, after interaction debounce/release.
- `reuse_planned`, `aa_reuse_prepared`, `surface_prepared`, `render_submit`:
  synchronous controller preparation, before background rendering is submitted.
- `base_first_ready` / `aa_first_ready`: the first callback is offered to its
  executor. This includes service scheduling/batching and is not a pure kernel
  timer. The first base callback can also be completion of an entirely cached frame.
- `base_publish`: target-frame base/ready pixels have been published to a visible
  staging image. Refined mode normally suppresses these publications.
- `aa_publish`: the first accepted AA tile has been copied to the surface.
- `base_complete`: the base-completion callback begins on the FX thread.
- `frame_promoted`: the completed staging image becomes the main displayed image.
- `complete`: the controller reports successful completion, including enabled AA.
- `*_post_layout`: the scene's post-layout pulse listener observes the marker
  mutation. **A JavaFX pulse is not a render-completion or display timestamp.**
- `*_screen_observed`: JavaFX Robot screen capture decodes the unique publication
  marker in the diagnostic strip. This is a compositor-capture proxy for the
  scene update, **not direct verification of every fractal pixel or physical panel
  scanout/photon latency**. It does not include input hardware latency either.

Each publication has a unique binary code and its original input/render identity.
Codes superseded before a pulse can remain unobserved; an earlier render cannot
be mistaken for the final render of a burst. The strip must show its calibration
sentinel and a confirmed black reset before each trial. The benchmark captures
only this 144x16 logical-pixel strip, not the desktop or fractal image. The window
stays on top during the run and closes on completion.

Screen capture runs on the FX thread as required by JavaFX Robot. Its cost is
recorded, along with the largest interval between successful probes. Observation
can be delayed by capture cost, pulse cadence, UI stalls, or compositor scheduling.
Always compare against a separate `noScreen` control; do not subtract median
capture cost to invent an unmeasured display latency.

Callback instrumentation stores counts, total/max queue wait and total/max callback
work per render/phase. It does not allocate an event for every AA tile. Summed queue
wait overlaps across callbacks and is **not** a sequential component of frame time.
The final callback's work includes synchronous AA preparation where applicable.
Recordings are bounded and queued callbacks retain their original recording epoch.

## Running

Compile once, then run measurements without overlapping tests or other benchmarks:

```sh
mvn -q -DskipTests compile

JAVA_TOOL_OPTIONS='-Xmx2g -Djavafx.cachedir=/tmp/fractallens-javafx-cache -Dfractal.gpu.enabled=false -Dfractal.latency.noScreen=true -Dfractal.latency.output=target/latency-control.csv' \
  mvn -q -Pinteraction-latency javafx:run

JAVA_TOOL_OPTIONS='-Xmx2g -Djavafx.cachedir=/tmp/fractallens-javafx-cache -Dfractal.gpu.enabled=false -Dfractal.latency.output=target/latency-screen.csv' \
  mvn -q -Pinteraction-latency javafx:run

python3 scripts/summarize_interaction_latency.py target/latency-control.csv target/latency-control-summary.csv
python3 scripts/summarize_interaction_latency.py target/latency-screen.csv target/latency-screen-summary.csv
```

macOS needs graphical access and screen-capture permission for the screen run.
A sandbox fallback to the software renderer without an accessible screen is not
a valid performance result. `-Dprism.verbose=true` reports the actual graphics
pipeline; the CSV's `requestedPipeline` is only the requested property value.

Settings: `fractal.latency.samples` (10), `warmup` (2), logical `width` (1200),
logical `height` (760), and comma-separated `gestures`
(`wheel,wheel-burst,pinch,trackpad,drag`), all with the `fractal.latency.` prefix.
Use a distinct output filename for each run. Modes run Refined then Fast. This is
a diagnostic sequence, not a randomized paired optimization speedup comparison.

Each trial resets the normal Mandelbrot/ICE view and waits for rendering to settle.
Pan/drag trials first zoom in twice, because the home view cannot pan beyond preset
bounds. It retains the production frame/AA cache behavior, including repeated-navigation
reuse; it is not a cold-cache formula benchmark. Exact resulting coordinates,
scale, iteration cap, sample pattern and physical buffer size are saved per trial.
One wheel event has deltaY=40. A wheel burst has six such events; pinch uses six
1.03 factors; trackpad pan uses six (8,3) deltas; drag uses six 8-point steps and a
release. The driver waits 16 ms between event dispatches; actual intervals can be
longer due to FX scheduling and are measured, not assumed.

The summary uses the first input for initial preview feedback, and the last input
plus the final render generation for settle/detail/completion latency. For drag
and pinch, last-input latency also includes the interval until release/finish.
It reports valid observation counts, medians and nearest-rank p95; absent markers
are missing values, never zero. A failed/incomplete run is rejected.

This experiment does not compare the previous AA implementation with the current
one. It locates present interaction delays; historical AA throughput speedups have
different workloads, cache state and measurement boundaries.

## Isolating the cached-frame planning cost

`ValidityScanBenchmark` constructs a completely ready validity mask and invokes
production `missingRowSpans` for the same 32x32 tile partition. No JavaFX, sample
calculation or AA is involved. Its second diagnostic path tests `isComplete()`
once before considering any tiles; it is not wired into the production renderer.
Both paths assert that no missing spans exist. Two warmups and five alternating
measured pairs run at each size.

```sh
mvn -q -DskipTests test-compile
java -cp target/test-classes:target/classes \
  com.shangin.fractal.render.ValidityScanBenchmark > target/validity-scan.csv
```

The classpath separator above is for macOS/Linux (`;` on Windows). Results and
interpretation are in [the measurement report](INTERACTION_LATENCY_RESULTS.md).
